Everything the framework governs, on one page

A reader's map of the rules distilled from the Invest project experience: who decides, how work is delivered in a closed loop, how documents stay authoritative, and how AI drift is kept out. Each card links to the Markdown file that owns the rules it summarizes.

Coverage

Thirteen governed aspects

The framework is a menu, not a mandate: tailoring is the first rule, and only modules supported by current evidence become active in a project. Inactive rules remain present, discoverable, and protected from deletion.

01 · Who decides

Roles, authority & partnership

  • Product Owner / Implementer / Reviewer / multi-writer role modules with activation conditions
  • Human keeps final authority: scope, risk, release, irreversible actions
  • Continuous plain-language guidance duty; five-class information discipline (user statement / observed / inference / proposal / unresolved)

AGENTS.md

02 · Day one

Greenfield initialization protocol

  • Adaptive interview, not a questionnaire; propose before writing
  • Eleven-state machine with no shortcut to "approved"; silence is not approval
  • Deterministic validation and honest evidence before completion

START_HERE.md

03 · The loop

Core feature delivery

  • Reconnect to purpose → shape together → agree test strategy → readiness gate → small increments → verify → close the learning loop
  • Discrepancy protocol: stop and report expected / observed / impact / options
  • Twelve-point Definition of Done, evidence-based completion

PROJECT_WORKFLOW.md § WF-CORE, WF-DOD

04 · Closed-loop control

Phased planning & delivery gates

  • Four planning tiers: roadmap → phase plan → current work → feature plan, each with one owner
  • Permanent work IDs that never encode mutable status
  • Delivery groups with a mandatory gate order and SHA-bound machine receipts; an approval never repairs an invalid order
  • Forward-data clock and gate-reachability checks so evidence thresholds stay achievable

WF-PLANNING Structure ref §9

05 · One owner per fact

Documentation management

  • Document map: brief, current state, work list, feature plans, ADRs, history, runbooks
  • One line of work has one detailed owner; other files hold pointers, never copies
  • History is not current state; a roadmap is not the active queue

WF-DOCS Structure ref §8–10

06 · Meaning stays exact

Language, terminology & translation

  • Six separate language responsibilities — never one vague "language" field
  • Engineering language of record; source evidence preserved in its original language
  • Terminology registry with stable term IDs and approved translations; translation is presentation, never new evidence

WF-COMMUNICATION

07 · Truth vs. views

Markdown truth, HTML translation

  • Maintained Markdown is authoritative; HTML and dashboards are derived, fail-closed views
  • Mandatory four-perspective control surface: management, business, operations, architecture/delivery
  • Missing evidence renders as an honest unavailable state, never as healthy

WF-VIEWS

08 · Keeping AI honest

Anti-drift defenses

  • Integrity manifest with hashes; immutable and managed-block file modes
  • Deterministic validators instead of self-declared success
  • Stable IDs for work, modules, terms, and views; context-loading rules so AI reads only what the task needs
  • WF-DRIFT: repeatable consistency checks once several modules or views exist

framework_manifest.json WF-DRIFT

09 · Shape of the repo

Structure & evidence-based tailoring

  • Complete directory and artifact catalog as a menu, never a mandate
  • Five decision states: selected_now, deferred_until_trigger, not_applicable, local_extension, framework_retained
  • Minimal greenfield starting set; source, data, derived output, and runtime state kept apart

PROJECT_STRUCTURE_REFERENCE.md

10 · Recoverable history

Version control

  • Complexity ladder from local Git to integration branches — activated by evidence, retired deliberately
  • Commit contract tied to permanent work IDs; secrets and runtime output stay out
  • Remote creation, visibility, push, and history rewrite are explicit human approvals

WF-VCS Structure ref §4

11 · When stakes rise

Data, operations, recovery & high impact

  • WF-DATA: authoritative and non-cleanable data discipline; tests never touch production
  • WF-OPS: unattended operation, locks, health, human takeover
  • WF-RECOVERY: verified backups and tested restore paths
  • WF-HIGH-IMPACT: human approval, independent verification, safe failure for consequential systems

WF-DATA / OPS / RECOVERY / HIGH-IMPACT

12 · Machine contracts

Profile, receipts & tools

  • project_profile.yaml: exact machine-readable record of approvals, activation, and unresolved decisions
  • Delivery receipts bound by SHA-256 to plans, validators, and approved scope revisions
  • Retained tools: initialization validator, receipt evaluator, atomic overview renderer

profile contract tools/

13 · Honest edges

Boundaries & non-goals

  • Greenfield projects only in 0.8; brownfield, import, and re-initialization are reserved, not improvised
  • No secrets in conversations, documents, or version control
  • Tailoring can remove ceremony, never human authority, honesty, or safety boundaries

Distilled, not invented
