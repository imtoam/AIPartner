01 · Who decides

Roles, authority & partnership

AGENTS.md is the team charter: the Product Owner holds final authority over purpose, scope, priority, risk acceptance, release, and every irreversible action; the Implementer is the single writer of source, control files, and history until the multi-writer module is activated. Optional modules add an independent read-only Reviewer (whose only write target is the review report) and multi-writer worktree rules with one integration owner.

The partnership duty is continuous: the AI must explain decisions in plain language, recommend with reasons, show alternatives, and keep the five information classes separate — user statement, observed fact, AI inference, AI proposal, unresolved. An inference never becomes a project fact without confirmation.

Sources: AGENTS.md

02 · Day one

Greenfield initialization protocol

START_HERE.md governs exactly one thing: turning an idea into an approved, verifiable starting structure. The AI facilitates an adaptive interview instead of handing the user a questionnaire, proposes before writing anything, and materializes files only after explicit approval — silence is never approval.

An eleven-state machine (uninitialized → interviewing → draft → proposed → needs_user_decision → approved_pending_materialization → materialized → verification_failed / blocked_by_environment → verified → complete) has deliberately no shortcut state called "approved". Completion requires deterministic validation with recorded evidence, and the protocol retires itself once initialization is complete.

Sources: START_HERE.md project_profile.example.yaml

03 · The loop

Core feature delivery

WF-CORE, kept in the workflow spine because every change needs it, runs an eight-step loop: reconnect to purpose, shape the feature together, agree the test strategy before implementation, pass the readiness and alignment gate, implement in small controlled increments, verify and check back, apply the discrepancy protocol when reality disagrees with the plan, and close the learning loop.

The discrepancy protocol forces a stop-and-report in six parts — expected, observed, impact, options, recommendation, decision needed — so an AI never silently picks which source of truth to ignore. WF-DOD defines twelve completion criteria from alignment through version control; passing tests does not excuse a product mismatch, and product alignment does not excuse missing verification.

Sources: PROJECT_WORKFLOW.md (spine: WF-CORE, WF-DOD)

04 · Closed-loop control

Phased planning & delivery gates

WF-PLANNING activates when two or more work lines compete. Planning has up to four tiers — roadmap, phase delivery plan, current work list, feature plan — and each fact has exactly one owner; other files hold pointers. Every feature and bug fix receives a permanent work ID before implementation, allocated from one registry, never reused, and never encoding mutable status.

When several work units need coordinated delivery, the phase plan owns delivery groups, group order, and dependencies. Implementation readiness is checked in one mandatory order (delivery_group → group_order → dependencies → approval/exact scope), and a project-specific validator must write a machine receipt whose SHA-256 digests bind the phase plan, validator, and every exact-scope revision. An approval never repairs an invalid order. Forward-data timing rules mark work whose evidence window cannot be recovered later, and every evidence threshold must be checked for reachability against its real generation funnel.

Sources: framework/workflow/WF-PLANNING.md documentation-catalog.md (§9.4 receipt contract)

05 · One owner per fact

Documentation management

WF-DOCS assigns every recurring question one owning document: why the project exists (product brief), what is true now (current-state document), what is active (current work list), what was agreed (feature brief), why decisions were made (ADRs), what happened (history). One line of work has one detailed owner; other documents point to it and must not copy its status.

History is not current state, a roadmap is not the active queue, and a temporary review report is never a permanent backlog — accepted findings move to permanent work IDs. The machine-readable record of approved paths, commands, and authority lives in project_profile.yaml; the human-readable facts blocks mirror it and disagreements must be reported, not silently resolved.

Sources: framework/workflow/WF-DOCS.md documentation-catalog.md (§8–10)

06 · Meaning stays exact

Language, terminology & translation

WF-COMMUNICATION replaces the vague single "language" setting with six separate responsibilities: conversation language, engineering language of record, code identifiers and typed values, human-view locales, source-evidence treatment, and translation policy. Externally sourced evidence keeps its original text, language, time, URL, hash, and lineage.

Translation is a presentation artifact: it never replaces source evidence, adds claims, changes typed values, or upgrades unknown/stale/insufficient data into a conclusion. A terminology registry with stable term IDs and approved translations activates when domain ambiguity or multiple locales justify it; a semantic change gets a new version instead of a silent redefinition.

Sources: framework/workflow/WF-COMMUNICATION.md

07 · Truth vs. views

Markdown truth, HTML translation

Maintained Markdown is the authoritative document layer; HTML pages, dashboards, and HTTP responses are derived views that declare their sources, generation time, freshness, and failure state. A view never becomes the only place a decision or fact exists, and generation fails closed — an old page must not silently stand in for missing truth.

Every initialized project ships one control surface, project-overview.html, with four mandatory perspectives from day one: management, business/domain operations, system operations, and architecture/delivery. A perspective without evidence shows an honest unavailable state with its reason, owner, and activation trigger — never a healthy-looking blank. Static HTML is the default; local HTTP, network exposure, and write-back are each separate approvals.

Sources: framework/workflow/WF-VIEWS.md

08 · Keeping AI honest

Anti-drift defenses

Drift is fought with machinery, not promises: framework_manifest.json pins every retained rule file with a SHA-256 hash (immutable mode) or a config-region-normalized hash (managed-blocks mode); tools/validate_initialization.py verifies integrity, profile contracts, activation consistency, and delivery receipts deterministically instead of trusting self-declared success.

Stable IDs for work items, modules, terms, and views keep references alive across rewrites. Context-loading rules stop an AI from re-reading the whole methodology for every task — and from treating history, roadmaps, or generated HTML as current truth. WF-DRIFT adds repeatable consistency checks once several modules or views exist, and the concept ownership registry in the workflow spine names the single normative owner of every cross-cutting concept so restatements cannot fork.

Sources: framework_manifest.json framework/workflow/WF-DRIFT.md PROJECT_WORKFLOW.md (concept ownership registry)

09 · Shape of the repo

Structure & evidence-based tailoring

The structure reference is a complete menu distilled from the Invest build — root files, source profiles, test layers, runtime directories, documentation artifacts — but presence in the catalog is never evidence a project needs the item. Every candidate gets one of five decision states: selected_now, deferred_until_trigger, not_applicable, local_extension, or framework_retained, each with evidence.

The minimal greenfield starting set is deliberately small: local Git, the profile, a product brief, a current work list with the first permanent work ID, and the generated overview. Everything else appears when a real consumer exists, and deferred needs record their trigger instead of materializing early.

Sources: PROJECT_STRUCTURE_REFERENCE.md (spine) root-files.md directory-catalog.md minimal-start.md

10 · Recoverable history

Version control

WF-VCS and the Git reference catalog define a complexity ladder — local Git, remote single writer, protected collaboration, integration branch — where each step up requires evidence and each non-default model records both an activation and a retirement condition. A branch isolates code; it is never the source of work status.

The commit contract ties every commit to a permanent work ID with one coherent verified change; secrets, production data, and runtime output stay out. Remote creation, visibility changes, pushes, publication, and history rewrites are external actions that always require explicit human approval.

Sources: framework/workflow/WF-VCS.md framework/structure/git-reference.md

11 · When stakes rise

Data, operations, recovery & high impact

Four optional risk modules activate when their conditions become real. WF-DATA: tests use temporary or synthetic data, diagnostics use read-only connections, append-only rules are enforced, and prospective, retrospective, synthetic, and migrated evidence stay distinguishable. WF-OPS: scheduled operation records its real runtime, uses locks and timeouts, makes repetition safe, and records failure evidence instead of treating failure as no data.

WF-RECOVERY verifies backups instead of trusting file presence and demands a tested recovery path. WF-HIGH-IMPACT draws the boundary between analysis and real-world action: risk-increasing actions require explicit human approval, critical logic gets independent verification, and learned or generated output never gains authority silently.

Sources: WF-DATA.md WF-OPS.md WF-RECOVERY.md WF-HIGH-IMPACT.md

12 · Machine contracts

Profile, receipts & tools

project_profile.yaml is the exact machine-readable record of approvals, module activation, structure decisions, unresolved decisions, and approved paths and commands — the contract is frozen in project_profile.example.yaml. Delivery receipts bind a pass result to SHA-256 digests of the phase plan, validator, and scope revisions, so a stale or edited file invalidates the receipt automatically.

Three retained tools enforce the contracts: tools/validate_initialization.py (framework integrity plus profile validation), tools/delivery_receipt.py (receipt evaluation and the machine constant of the gate order), and tools/render_project_overview.py (atomic generation of the overview from declared sources).

Sources: project_profile.example.yaml validate_initialization.py delivery_receipt.py render_project_overview.py

13 · Honest edges

Boundaries & non-goals

Version 0.9 initializes greenfield projects only; brownfield adoption, import, and re-initialization are reserved modes, not permission to improvise. The framework never collects or stores secrets — only their purpose, delivery mechanism, and variable names.

Tailoring can remove ceremony but can never remove human authority, information honesty, permanent work identity, evidence-based completion, or the duty to stop on a material discrepancy. The generated overview and this page are derived views; the Markdown remains the project's truth.

Sources: START_HERE.md (§0–1) README.md
